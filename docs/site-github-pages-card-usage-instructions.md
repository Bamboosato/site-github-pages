# アプリカードの特徴表示・詳細ページの利用条件 改善指示書

作成日：2026-10-02  
補足：BBCafe Appの新規利用条件をユーザー確認に基づき追記  
表示方針の改訂：カードを簡潔に保ち、利用条件と補足は詳細ページへ掲載  
対象repository：https://github.com/Bamboosato/site-github-pages  
確認したmain：`88443d25dbd21780cb9ad8a4fcb65a7769a2dd59`

## 1. 目的と今回の範囲

カードでアプリの概要と特徴を比較し、詳細ページで利用条件や準備を確認できるようにする。

今回の対象は以下の2点。

1. ログイン等の利用条件と必要な準備を、各アプリの詳細ページで伝える。
2. 端末内処理・登録不要・オフライン対応等の特徴を、技術タグより先に伝える。

ユーザーはカテゴリ変更を保留としている。カテゴリ名・カテゴリID・アプリのカテゴリ配置は変更しない。テニス系アプリの再編や旧版／後継の整理も今回の範囲に含めない。

サイトのUI改善であり、リンク先アプリの認証・利用制限・機能を変更する作業ではない。

## 2. 現状と問題

`src/components/AppCard.astro`は、カテゴリ、アプリ名、短い説明、技術タグ、更新日、アクションを表示している。利用条件を表すメタデータは存在しない。

BBCafe Appは紹介本文に認証の説明があるが、新規利用の準備条件を詳細ページでまとめて確認できるようにしたい。アプリ側のREADMEではFirebase Authログインを使い、ユーザーはFirebase Consoleで作成し、アプリ内の新規登録画面はないと説明されている。ユーザーの最新指定に従い、カードに条件案内や登録手順を追加しない。

ユーザーからの追加確認（2026-10-02）：BBCafe Appに新規登録する場合は、事前にLINE公式アカウントの取得と、アプリ管理者によるアカウント登録が必要。これは新規利用の準備条件であり、既存利用者がログインするたびに行う作業ではない。

また、現在のタグはReact・TypeScript等の技術情報であり、一般利用者にとって「何を準備すれば使えるか」「画像や文書はどこで処理されるか」が見えにくい。

## 3. 表示方針

カードの順序は次を基本とする。

1. カテゴリ
2. アプリ名
3. 短い概要
4. 利用者向け特徴（短いチップ、最大3件）
5. 技術タグ（既存情報を維持し、視覚的に控えめにする）
6. 最終更新日
7. アプリを開く／詳しく見る

カードは概要と短い特徴を読むための表示とし、ログイン条件、アカウント登録条件、モデル取得などの補足文を載せない。特徴は落ち着いたチップ表示を基本とする。

詳細ページには「利用条件・使い始めるには」（英語例：Requirements & getting started）の節を設け、ログインの必要性と準備条件、処理やオフライン利用の補足をまとめる。色だけで意味を表さず、条件を文字で記載する。赤色や警告アイコンによって通常のログイン条件を危険のように見せない。

Homeのピックアップ・最近更新、Apps一覧、カテゴリ別一覧で同じカードコンポーネントを利用し、表示を揃える。詳細ページは同じメタデータを利用して特徴・利用条件・補足を表示し、カードと内容の意味を一致させる。情報の表示量はカードと詳細ページで分ける。

### BBCafe Appの詳細ページの表示例

- 利用条件：**ログインが必要**
- 補足：**新規利用には、LINE公式アカウントの取得と、アプリ管理者によるアカウント登録が必要です。**

詳細ページには、既存利用者は登録済みアカウントでログインすることと、アプリ内に新規登録画面がないことも説明する。カードには上記のログイン案内・補足を表示しない。表示する特徴が確認できなければBBCafe Appのカードに特徴を無理に追加しない。

英語補足例：**To start using the app, you need to obtain a LINE Official Account and have your account registered by the app administrator.**

カード・詳細の既存の「アプリを開く」を維持する。ログイン不要に見える「今すぐ使う」等へ変更しない。未指定の問い合わせ先や登録依頼リンクを追加しない。

### Face Icon Makerの表示例

- カードの特徴：**端末内処理／登録不要**
- 詳細ページの補足：**初回利用時には処理用モデルの取得が必要です。**

写真を送信しないことと、モデル取得にネットワークを使うことを区別する。キャッシュ依存のモデル再利用を理由に、オフライン対応を確定表示しない。

### Slide Puzzle Labの表示例

- カードの特徴：**端末内処理／オフライン対応**
- 詳細ページの補足：**オフラインで遊ぶには、初回のオンライン利用が必要です。**

「登録不要」を追加する場合も、対象アプリのソース等で確認してから追加する。

## 4. データモデル

UI内でアプリ名や`appId`に応じた条件分岐を書かない。アプリMarkdownのfrontmatterへ、利用条件と特徴を追加する。既存MarkdownがそのままBuildできるよう、新項目は省略可能にする。

以下の構成を推奨する。既存構造との整合性を保てる同等の構成への調整は可。

```yaml
# BBCafe Appの例
access: login-required
usageFeatures: []
usageNote: "新規利用には、LINE公式アカウントの取得と、アプリ管理者によるアカウント登録が必要です。"
```

```yaml
# Face Icon Makerの例
access: open
usageFeatures:
  - on-device-processing
  - no-registration
usageNote: "初回利用時には処理用モデルの取得が必要です。"
```

```yaml
# Slide Puzzle Labの例
usageFeatures:
  - on-device-processing
  - offline-after-setup
usageNote: "オフラインで遊ぶには、初回のオンライン利用が必要です。"
```

### access

| ID | 意味 | 日本語表示 | 英語表示 |
| --- | --- | --- | --- |
| `open` | 紹介対象の主要機能をログインせず利用できる | 条件案内は表示しない | 条件案内は表示しない |
| `login-required` | 主要機能にログインが必要 | ログインが必要 | Login required |
| `role-dependent` | 主催者／参加者等の役割により条件が異なる | 役割によりログインが必要 | Login depends on your role |
| `unknown` | 条件未確認 | 案内は表示しない | 案内は表示しない |

この表の条件ラベルは詳細ページで使い、カードには表示しない。省略時は`unknown`とする。未確認を`open`として扱わない。`open`を設定する場合も根拠を残す。

### usageFeatures

| ID | 日本語表示 | 英語表示 |
| --- | --- | --- |
| `on-device-processing` | 端末内処理 | On-device processing |
| `no-registration` | 登録不要 | No registration required |
| `offline-after-setup` | オフライン対応 | Offline after setup |

省略時は空配列。初期実装ではこの3種類に絞る。特徴を3件埋めるために未確認項目を追加しない。

`on-device-processing`は、利用者が入力した画像・文書・テキスト等の主要処理がブラウザー内で行われることを意味する。アプリ配信やモデル取得を含めた通信ゼロを意味しない。

`no-registration`は、紹介する主要機能をアカウント作成なしで利用できることを意味する。事前作成アカウントでのログインが必要なBBCafe Appには付けない。役割により異なる場合は、無条件の登録不要表示を避け、補足で範囲を説明する。

`offline-after-setup`は、初回オンライン準備後に紹介する主要機能をオフラインで利用できることを意味する。PWA対応だけを根拠に付けない。単に過去のページがキャッシュされるだけの場合も付けない。

### usageNote

利用条件や特徴に必要な補足を記載する言語別の短文。空文字は許可しない。詳細ページにだけ表示し、カードでは表示しない。さらに詳しい説明は詳細本文へ記載する。重要な前提条件を省略記号で隠さない。

日本語／英語で`access`と`usageFeatures`は一致させる。`usageNote`は翻訳する。片方だけに補足がある状態を検出する。表示ラベルは`src/i18n/ui.ts`等の共通辞書へ集約する。

## 5. 各アプリの情報確認

対象アプリの最新README、現在のソース、必要に応じた公開画面で確認してからメタデータを設定する。今回の確認で利用可能な出発点は以下。

| アプリ | 出発点として使える根拠・注意 |
| --- | --- |
| BBCafe App | READMEにログイン、管理者側でのユーザー作成、アプリ内新規登録なしの記載。さらに2026-10-02のユーザー確認で、新規利用にはLINE公式アカウント取得とアプリ管理者によるアカウント登録が必要と確定。両方を詳細ページの利用条件に表示する |
| Face Icon Maker | READMEに端末内画像処理、ユーザーアカウントなし、初回モデル取得の記載。端末内処理・登録不要を候補とする |
| Slide Puzzle Lab | READMEに端末内画像処理と初回アクセス後のオフライン利用の記載。対応範囲を確認して表示する |
| App Reveal Lab | READMEにクライアント内画像処理とPWAによるオフラインの起動・描画・動画出力の記載。現在の実装と一致するか確認する |
| MatchupLab | サイト紹介と確認記録に、アカウントを使わないローカル保存・組合せ生成の記載。アプリREADMEには移行前の記述があるため現在のソースを優先する |
| Local Document Preprocessor | サイト紹介では文書処理がブラウザー内。入力データの扱いをアプリ側で確認する |
| Local PII Masker | サイト紹介ではブラウザー内のマスキング。対応表の保存と復元も含めて表示の範囲を確認する |
| RSVP Hub | サイト紹介では主催者ログインと招待リンクからの回答。主催者と回答者の条件を区別し、一律のログイン必要／登録不要表示を避ける |
| 残りの掲載アプリ | 同じ基準で確認する。PWA・IndexedDB等の技術名から利用条件を推測しない |

全14件に対して「何を確認したか／設定した項目／未確認項目」を報告する。すべてのカードに同じ数の特徴がある必要はない。

根拠の記録は既存の`docs/public-repositories.json`または`docs/content-maintenance.md`の運用と整合させ、アプリごとに参照したrepoパス、commit、確認日、主張の対象範囲を残す。BBCafe Appの新規利用条件は「2026-10-02、ユーザーによる運用条件の確認」と記録し、READMEだけから確認した事項と区別する。利用者向けカードに根拠commitや実装用パスを表示する必要はない。

## 6. 実装対象と検証ルール

主な変更対象：

- `src/lib/schema.ts`：省略可能なaccess・usageFeatures・usageNoteのスキーマ
- `src/lib/validation.ts`：言語間の共通項目検証、未知IDや矛盾の検出
- `src/i18n/ui.ts`：条件・特徴・リストのアクセシブル名の翻訳
- `src/components/AppCard.astro`：短い特徴チップの表示（access・usageNoteは表示しない）
- `src/components/AppDetail.astro`：特徴・利用条件・補足の表示
- `src/styles/global.css`：条件案内・特徴チップのスタイル
- `src/content/apps/{ja,en}/`：確認したアプリのメタデータ
- 既存テストと運用ドキュメント

未知のaccess／特徴ID、重複した特徴ID、4件以上の特徴、日英の共通項目不一致を検出する。`login-required`と無条件の`no-registration`の併用を禁止する。`role-dependent`の場合は条件の対象を説明する`usageNote`を必須とする。

詳細ページのオフライン対応には初回オンライン準備の補足を付ける。カードでは「オフライン対応」の短い表示とし、「初回から通信不要」等の未確認の強い表現へ置き換えない。

条件や特徴が省略されたアプリでは、空の見出し・枠・空リストを表示しない。情報不足を公開画面で「登録不要」等に置き換えない。

技術タグは維持するが、利用者向け特徴の方が先に目に入るようにする。カード全体の装飾や情報量を増やしすぎない。

サイト紹介の補足追加だけでは、アプリの`updatedAt`を変更しない。アプリ機能の更新として`src/content/updates/`へ新規エントリを追加しない。今回確認した実際のアプリ変更が別途ある場合は、その根拠に基づき扱う。

## 7. 確認観点と受入条件

### データと正常・異常系

- 既存データで新項目を省略してもBuildできる。
- 条件だけ、特徴だけ、両方あり、両方なしのデータを扱える。カードには特徴だけ、詳細には条件と補足も表示される。
- BBCafe Appの詳細ページにログイン条件と、新規利用に必要な「LINE公式アカウント取得」「アプリ管理者によるアカウント登録」の両方が表示される。
- BBCafe Appのカードには上記の条件案内・補足を表示しない。
- BBCafe Appの詳細では既存利用者のログインと新規利用の準備条件を区別し、日英で同じ条件を説明する。
- 日英のID一致・補足の翻訳対応を検証できる。
- 未知ID、重複、件数上限超過、矛盾、補足欠落を検出できる。

### UI・機能・非機能

- Home／Apps／カテゴリ一覧／詳細で意味が一致する。
- 320px・390px・768px・Desktopでカードの英語チップがはみ出さず、詳細ページの条件案内と重要な補足が全文読める。
- 英語の長い文でカード内のアクションが崩れない。
- 読み上げでカードの特徴と技術情報、詳細の利用条件を区別できる。
- チップは説明用の静的表示とし、クリックできるフィルターのように見せない。
- 条件案内を追加してもリンク操作・キーボードフォーカス・日英切替が維持される。
- 表示に外部APIや閲覧時JavaScriptを追加しない。
- カテゴリ名・ID・所属、掲載アプリ集合、公開URLを維持する。

既存の`npm run verify`を実行する。条件・特徴の表示、日英ページと導線を代表ケースで確認する。追加された文言は内部リンク構成を変更しないが、URL・言語・設定に変更が生じた場合はAGENTS.mdに従い`npm run verify:bases`も実行する。

状態遷移は言語切替と一覧から詳細への遷移を対象とする。同じブラウザーへの操作は逐次実行する。入力データのプライバシーやオフライン対応を表示する場合、READMEとソースの確認だけか、実際に通信・オフライン動作まで確認したかを区別して報告する。

## 8. 実装順序と完了報告

1. 対象repositoryと最新main、AGENTS.mdを確認する。
2. 全14件の根拠を確認し、表示する条件・特徴を決める。
3. スキーマ・翻訳辞書・データ検証を追加する。
4. 共通カードに特徴、詳細ページに利用条件と補足を追加する。
5. 日英Markdownと根拠記録を更新する。
6. 既存検証と代表画面の表示確認を実施する。

完了報告には、実装内容、各アプリの表示項目と根拠、未確認情報、検証結果、代表的な日英カード画像を含める。カテゴリ変更を混在させない。
